# RFC 0040: Fen's interrupt latency, measured

How long Fen's kernel holds interrupts off, what holds them off, how often
interrupts come, and how long the kernel goes between the moments it
could look at a lazy event: the measurements behind
[RFC 0040](../0040-rfc-interrupts.md)'s latency table and its kernel
conventions ([7](../0040-rfc-interrupts.md#7-the-kernels-conventions),
[8](../0040-rfc-interrupts.md#8-latency)). The numbers are in
[fen-latency-results.md](fen-latency-results.md), generated by
`heron fen irq --write` ([studies/fen/irq.py](../../studies/fen/irq.py)).

## How it was measured

- **Fen** ([report 0036](../0036-report-fen.md)) on its simulator, at
  6 MHz with the simulator's reference timing, run one instruction at a
  time.
- **A span with interrupts held off** runs from I going clear to I being
  set again. It is named after what started it: the vector the CPU
  entered through (a system call, an interrupt, a fault), or a `DI`.
- **A random arrival's mean wait:** an interrupt that arrives at a random
  moment lands in a span of length T with probability T over the whole
  time, and waits T / 2 on average, so its mean wait is the sum of T²
  over twice the time. It leaves out the handler's own time.
- **The gaps** between thread switches (a change of register bank) and
  between returns to user mode bound how long a lazy event waits for a
  kernel that only looks at its rings then.
- **Five workloads:** boot, eight short commands at the serial shell,
  the kernel's benchmark `kbench`, two idle seconds, and the desktop with
  a click, some typing and a drag.

## What it found

### Fen's kernel holds interrupts off for milliseconds at a time

Fen runs every kernel path with interrupts off, as report 0036 says.
Most paths are short: the median span is 41–46 µs in every busy
workload, the IPC paths 40–80 µs. A few system calls run much longer:

| System call | Longest | What it does with interrupts off |
|---|---:|---|
| `vm_alloc` | 46 ms (`kbench`), 4.2 ms (commands) | zeroes every page it allocates |
| `boot_spawn` | 40 ms, at boot only | builds the first processes |
| `vm_map_phys` | 32 ms (desktop) | maps the video card's 2 MB, a page at a time |
| `exit` | 3.4 ms | frees a process |
| `ipc_write`, `ipc_read`, `vm_write` | 0.5–1.8 ms | copies between address spaces |

So the mean wait of an interrupt at a random moment is about 145 µs at
the shell and 0.7 ms on the desktop, but 4 ms during boot and 6.5 ms
under `kbench`, where big allocations dominate. The longest waits, 40–46
ms, are four or five of the timer's ticks. Fen counts the ticks it missed
from its counter, so its clock stays right, but every slow interrupt's
worst case is set by these calls.

### Messages need the kernel at IPL 6, not interrupts off

RFC 0040's message level gets in while the kernel holds the slow levels
off only if the kernel holds them off with IPL, not with I. Fen today
keeps I clear throughout its kernel, so a message would wait as long as
any slow interrupt: up to 46 ms. Under RFC 0040's convention, the kernel
would set IPL 6 and then I at each entry (two instructions), and a
message would get in within an instruction or two except while an
exception is being entered or left. Fen uses no `SPL` today, only `EI`
and `DI` around its idle `HALT`.

### The long spans have cheap cures, separate from RFC 0040

- **Zeroing pages in the I/O processor's background** (RFC 0027's other
  uses) takes most of `vm_alloc`'s time away: zeroing is 4,619 of a
  demand-zero fault's 4,753 cycles in report 0020, so a 46 ms allocation
  would shrink to around 1.5 ms (*estimate*).
- **A point between pages** where interrupts are let in, in `vm_alloc`,
  `vm_map_phys`, `exit` and `vm_write`, bounds a span by one page's work:
  about 0.8 ms with the kernel zeroing, tens of µs without.
- **Copies through the I/O processor** take `ipc_write` and `ipc_read`'s
  copying out of the kernel.

### Interrupts are rare

At most about 500 a second in all: the CF card 87–335 while files load
(Fen's driver takes one a sector), the timer 77–100, the UART up to 67
on the serial console, PS/2 15 on the desktop. Handed to user-level
drivers at 500–640 cycles each, 500 a second is about 5% of the 6 MHz
machine. With the I/O processor moving whole requests, the CF card's
would drop to one per request. So batching slow events saves little in
interrupts; its value is in fewer hand-offs to drivers.

### Lazy events wait milliseconds when the machine is busy

Between thread switches the median gap is 4–165 µs, and 90% of gaps are
under 1.2–2.5 ms; returns to user mode are as frequent. The longest gaps
(0.5–0.9 s) are idle time, when the kernel sets its wake-me words and
lazy events become slow ones. So a lazy event waits a few milliseconds
while the machine works, and the tick (8–16 ms) bounds it.

### Fen's level numbers are one below RFC 0029's

Fen's board sets mask bit L − 1 for RFC 0029's level L, and Fen's kernel
and report 0036 call that level L − 1. Fen's timer, its "level 6", is
RFC 0029's level 7, its UART RFC 0029's 6, its CF card 5, PS/2 4 and
video 3. Fen's vector table is consistent with RFC 0029's (level L at
`0x40` + 4(L − 1)), so nothing misbehaves; only the names are shifted.
Under RFC 0040's convention Fen's timer would move from RFC 0029's level
7 to 6.

## What it means for RFC 0040

- **The latency table's slow row** (up to about 1 ms) holds for Fen at the
  shell. With today's long system calls it is up to 46 ms. Either number
  is far more than the I/O processor's few µs.
- **The message level only pays** if the kernel moves to IPL 6 at entry,
  which is cheap.
- **The long spans** are worth fixing in Fen whatever RFC 0040 decides:
  background zeroing and a point between pages.
- **Batching** saves little, at Fen's interrupt rates.
- **Lazy events** wait a few ms when busy, and are bounded by the tick.

## Caveats

- One kernel, on a simulator: the spans scale with the CPU's cycles, and
  the hardware of RFC 0031 times differently.
- Five workloads, short ones: a busier machine, more processes or a
  network would change the rates, though probably not the shape.
- The waits leave out each handler's own time and the hand-off to a
  user-level driver (report 0020's 500–640 cycles).
