# Report 0018: A Lisp on draft 1b, and what it wants from the instruction set

The [lisp study](../studies/lisp/README.md) is a small Lisp for draft 1b,
built to find out what a dynamically typed, garbage-collected language
needs from the instruction set and the system. It has an interpreter and a
compiler that both run on the machine, and an experimental ISA variant.
This report says what was built, how fast it is, where the cycles go, and
which changes to the ISA and the system would pay. The per-program tables
are in [performance.md](0018-report-lisp/performance.md), generated by
`heron lisp report --write`.

All cycles are for D32-separate, the configuration of the 213-chip 1b
hardware ([report 0012](0012-report-draft-1b-hardware.md)), which runs at
about 3 MHz.

## Summary

- **Both an interpreter and a compiler run on the machine.** The compiler
  is written in the Lisp and compiles itself. Compiled code is 13–24 times
  faster than interpreted (19 times on the geometric mean).
- **1b's misaligned-access trap is the most valuable feature for the
  Lisp.** With pointers tagged in their low bits, `car`, `cdr` and calls
  check their operand's type for free. Without the trap, the checks would
  cost 16% of compiled cycles (up to 35%) and 19% of interpreted ones.
  Draft 2 should keep the trap precise, with the faulting instruction's
  address saved.
- **A tagged register mode** (the reserved mode E: an operand that must be
  an integer, and `ADD`/`SUB` that trap on overflow) saves 6.4% of
  compiled cycles on the geometric mean, up to 16% on arithmetic-heavy
  programs.
- **Guard pages** would save 5.0% (the stack limit) and 1.8% (the heap
  limit) of compiled cycles, at no cost beyond a paged MMU
  ([RFC 0010](0010-rfc-ideas-os.md#3-mmu)).
- **What 1b already has that matters:** `CALL [r1 + 1]` through a code
  word (1.3% over a load and a register call), one-parcel stack slots, and
  auto-increment for pushes, pops and `cons`.
- **Not worth it:** a one-parcel form for the pair offsets (1.1%) and a
  register for the heap limit (0.9%).

## What was built

- **The language** ([language.md](../studies/lisp/language.md)): a
  Lisp-1 in the style of early Scheme. It has 31-bit integers, pairs,
  symbols, strings, vectors, closures, `define`, `let`, named `let`,
  `letrec`, `cond`, `case`, `do`, quasiquote and macros. Errors print a
  message and the offending values and go back to the top level.
- **The runtime** ([implementation.md](../studies/lisp/implementation.md)):
  3,800 lines of 1b assembly, 8 KB of code. It has a reader, a printer,
  the primitives, a Cheney copying collector and an S-expression
  interpreter.
  - Values carry a 3-bit tag in their low bits.
  - The collector's roots are the stack, scanned word by word without
    stack maps, and the registers `r1`–`r8`.
- **The compiler** ([compiler.md](../studies/lisp/compiler.md)): 1,235
  lines of the Lisp. It's a one-pass compiler in the style of the early
  Lisp compilers:
  - flat closures;
  - known calls for `letrec` functions;
  - inline primitives, with every type check the interpreter makes;
  - no register allocation: every variable lives in a stack slot.

  Compiled by itself, it and the prelude are 50,524 bytes of 1b code.
- **The tests:** 12 benchmarks in the style of Gabriel's and 10 tests of
  the language, each checked against an independent reference interpreter
  in Python. They run interpreted, compiled, and compiled with the tagged
  mode.

## Interpreted and compiled

| | Interpreted | Compiled |
|---|---:|---:|
| tak | 208 M cycles (70 s) | 8.5 M (2.8 s) |
| boyer | 1,056 M (5.9 min) | 54 M (18 s) |
| Speed-up, geometric mean | | 18.9 |
| The collector's share | 0.3–3.1% | 0–15% |

- **Compiling on the machine is practical.** Compiling a program takes
  8–20 thousand cycles per byte of source, so a 1 KB file compiles in
  3–7 s at 3 MHz. Making the saved image takes 1.7 billion cycles, or
  9.5 minutes. That's loading the compiler, interpreted, then letting it
  compile itself (1.2 billion of the cycles) and the prelude.
- **The collector's share is low**, with 384 KB semispaces in the 1 MB of
  RAM: at most 15% of compiled cycles. The interpreter allocates more
  (its environments are frames in the heap), but everything else it does
  is slower still, so its collector's share is smaller.

**Where the interpreter's cycles go.** Applying procedures (`ev_app`,
`apply_fun`, `apply_stack`) and evaluating arguments (`eval_into`,
`eval_one`) take over half. Looking up variables takes 16.5%
(`ev_var`), even though most global references skip the environment
search: a symbol never bound locally goes straight to its value cell.
The interpreter dispatches special forms through `JMP [table + r]`.

**Where the compiled cycles go** (mean share of compiled cycles; the
largest in brackets):

| Category | Share | |
|---|---:|---|
| Variables, constants and temporaries: stack slots, pushes and pops | 29.3% (36%) | The cost of having no register allocation |
| Calls: setting up, entering, returning, reading the global | 24.6% (42%) | The entry alone is 10%: the argument count, the stack limit and saving the arguments |
| Integer checks (`type`) and overflow checks | 8.5% (25%) | What the tagged mode removes |
| `car`, `cdr` and vector elements | 4.8% (12%) | Checked for free by the alignment trap |
| Allocation inline | 3.4% (13%) | Plus `cons` and the collector in the runtime |
| Unbound-global checks | 2.0% (3.5%) | |
| Everything else compiled | 6.5% (15%) | Tests, arithmetic, predicates, vector bounds |
| The runtime's routines and the collector | 21% (46%) | Primitives that aren't inlined, such as string operations, `assq` and `length` |

A better compiler would shrink the first row the most. That would make the
checks and the call overhead, the parts an ISA can help with, a larger
share than these numbers show.

## What 1b gives the Lisp already

**Misaligned-access traps as type checks.**

- A pair `p` has the tag `001`: its car is at `[p - 1]` and its cdr at
  `[p + 3]`. Those word addresses are aligned only if `p` really is a pair.
- Every other heap object has the tag `011` and a code word at `[p + 1]`,
  and a call is `CALL [r1 + 1]`.
- So `car`, `cdr` and calls are single instructions, and anything of the
  wrong type takes an address-error trap. The handler decodes the
  faulting instruction (the displacement says which check failed, the
  base register holds the culprit) and reports a Lisp error.

Without the trap, each of these would need a check:

```
        MOV  r9, r1
        AND  r9, #3
        CMP  r9, #1
        BNE  not_a_pair
```

The what-if costing (below) puts that at **16.0%** of compiled cycles on
the mean. It ranges from 0.7% (sieve, which uses vectors) to 34.6% (meta,
an interpreter written in the Lisp). For the interpreter it's 19.3%.

> **Erratum (2026-10-16).** Two bugs that [report 0032](0032-report-lisp-egret-draft-2.md#three-bugs-carried-over-from-1b)
> found are now fixed on 1b as well: `apply` checks the stack limit
> before it pushes the arguments, and a compiled `cons` that finds the
> heap full calls the runtime's `cons`, which checks the limit again
> after collecting. The check in every `apply` makes meta's compiled run
> 0.4% slower, so its share above is now 34.4%. The other numbers in
> the text still match [performance.md](0018-report-lisp/performance.md),
> whose figures move by less than 0.1% elsewhere.

- That's an upper bound for a compiler that inferred types and dropped
  checks it could prove unneeded. This one doesn't.
- The trap must be **precise**: the saved PC must be the faulting
  instruction's own address, with nothing changed yet. Draft 1's
  restartability rules already guarantee that.
- It must also be **decodable**: the handler reads the instruction to find
  the register and the displacement.

**`CALL [r1 + 1]`**, the memory-indirect call. 1a would need a load and a
`CALL r`; that costs 1.3% of compiled cycles on the mean (2.5% at most).

**One-parcel stack slots and auto-increment.**

- Variables are mostly `[sp + 4R]`, one parcel; 1a's short `LD` has the
  same reach.
- Pushes and pops are `-[sp]` and `[sp]+`.
- `cons` is `ST r3, [r14]+`, `ST r4, [r14]+`, `LEA r1, [r14 - 7]`.

The pushes and pops are most of the 12% of compiled cycles that go to
temporaries.

## Experiments

Each change was costed from measured runs:

- **The tagged register mode** was built and measured. It's draft 1b's
  reserved mode E, specified in
  [the appendix](#appendix-v1bx-draft-1b-with-a-tagged-register-mode) as
  the ISA `v1bx`, run by the simulator.
- **The other changes** were costed without building them
  (`whatif.py`). For each one, the instructions it affects are picked out
  of the per-instruction counts of the measured runs. They're then costed
  again, as they would be after the change, through the same timing model,
  or not at all if the change makes them unneeded.

| Change | Compiled: mean (range) | Interpreted | What it would take |
|---|---:|---:|---|
| Tagged register mode (v1bx) | **6.4%** geometric mean (0–16%) | – | Mode E in 1b; about one chip of gates and microcode |
| The stack limit by a guard page | **5.0%** (2.9–7.2%) | 1.2% | A paged MMU |
| The heap limit by a guard page | **1.8%** (0–5.2%) | 0.1% | A paged MMU |
| The argument count checked for free | 1.8% (0–3.5%) | – | An upper bound; no mechanism proposed |
| Unbound globals caught for free | 2.0% (0–3.5%) | – | Software, for calls (below) |
| One-parcel `[R - 1]` and `[R + 3]` | 1.1% (0–2.7%) | 1.7% | Encoding space 1b doesn't have |
| The heap limit in a register | 0.9% (0–2.6%) | 0.1% | A register |

The changes touch different instructions, so their savings roughly add up.
The tagged mode and the two guard pages together come to about 13% of
compiled cycles.

### The tagged register mode

With mode E, `(+ a b)` is one `ADD.T r1, r3` instead of two three-instruction
tag checks, an `ADD` and a `BVS`. `(< a b)` is a `CMP.T` and a branch,
`(zero? a)` is `CMP.T r1, r0`, and a single check (a vector index) is
`MOV.T r9, r1`. A non-integer operand or an overflow traps through a new
vector, and the handler finds the culprit by decoding the instruction, as
for address errors.

| Program | Change |
|---|---:|
| fib | −16.3% |
| nqueens | −13.8% |
| sieve | −13.3% |
| tak | −12.1% |
| destruct | −7.3% |
| sort | −6.2% |
| closures | −2.8% |
| strings | −2.6% |
| boyer, deriv, div, meta | 0 to −0.2% |
| **geometric mean** | **−6.4%** |

- **The cost.** The timing model costs a tagged operation like the same
  operation on registers. If the microcode needs an extra cycle to check
  before writing the result back, the gain is 5.6% instead of 6.4%.
- **The hardware.**
  - The check is an OR of the operands' bit 0, plus the ALU's overflow,
    fed through the condition latch's spare source.
  - The microcode's 3-bit condition field is full, so the latch is the
    way in.
- **The cost in encoding.** It uses the last reserved mode in 1b. In 1a,
  op 1's 16 ALU functions are all taken, so tagged `ADD`, `SUB`, `CMP` and
  `MOV` would go in op F.
- **The interpreter gains little.** Its arithmetic is in a few
  primitives, which take at most 4% of its time (fib).

### Guard pages for the stack and the heap

**The stack.**

- Every compiled function's entry compares `sp` with a limit in memory
  and branches: `CMP sp, [stack_limit]` / `BLO`. The interpreter checks in
  `eval`.
- That's 5.0% of compiled cycles: half the entry cost, and 7% in tak and
  fib, which are all calls.
- An unmapped page below the stack would catch an overflow as a page
  fault instead. The handler would turn it into a Lisp error, as the
  address-error handler does.

**The heap.**

- `cons` compares the heap pointer with a limit before its two stores.
- With an unmapped page after each half of the heap, the first store
  faults when the half is full. The fault handler collects and restarts
  the store.
- Cells are 8-byte aligned, so a pair never straddles the boundary. Only
  `cons` would change; larger objects go through `alloc`, which can keep
  its comparison.

Both need restartable stores, which draft 1 already has, and a paged MMU.
RFC 0010 recommends the flat page map, and with it guard pages cost
nothing more. Protection regions with a limit register would do for the
stack alone.

### The smaller ones

- **Unbound globals.** Every read of a global compares it with the unbound
  marker. Many global reads are calls, which go through the value's call
  slot anyway.
  - If the unbound marker were an object whose call slot reports the
    error, calls wouldn't need the check, with no hardware change.
  - The error message would need another way to find the variable's
    name, for instance by decoding the load before the call.
- **The argument count** is checked at every entry except known calls.
  The 1.8% is what it would save if it were free, and there's no cheap
  hardware way to do that.
- **One-parcel pair offsets** and **the heap limit in a register** save
  about 1% each. Neither is worth an encoding or a register.

## For draft 2

RFC 0006 recommends basing draft 2 on 1a. For the Lisp, that means:

> **Erratum (2026-10-15).** RFC 0006 no longer recommends 1a: draft 2
> builds on 1b (Emily), which already has the trap, the memory-indirect
> call and auto-increment. The points below are what a 1a-based draft 2
> would have needed ([RFC 0006, section 4](0006-rfc-ideas-isa.md#4-what-a-1a-based-draft-2-would-want)).

- **Keep the misaligned-access trap, precise.** It's the largest single
  effect measured here.
  - 1a's short word loads scale their offset by 4 (`[rs + 4o]`), so
    `[p - 1]` and `[p + 3]` take the 2-parcel long form, as they do in 1b.
  - That's no loss against 1b: the one-parcel form would only be worth
    1.1%.
- **The memory-indirect call** is worth 1.3%. 1a would lose it unless it
  gets `CALL [rs + d]`.
- **Pushes and pops:** auto-decrement and auto-increment, already
  recommended for 1a's op F, matter here too.
- **Tagged arithmetic** fits in 1a's op F, alongside them.

The compiler targets only 1b, so these are estimates from 1b runs. A 1a
back end would measure draft 2's base directly.

**Memory.** The Lisp fills the 1 MB:

| Area | Size |
|---|---|
| Two heap halves | 384 KB each |
| Stack | 64 KB |
| Code space | 68 KB |
| Constant space | 32 KB |
| Symbol space | 31 KB |

- Symbols live in the first 32 KB, where a 16-bit absolute address reaches
  them, so a global access is a 2-parcel instruction. That makes room for
  about 990 symbols; the compiler and the prelude use 485.
- A larger system would put symbols further up and pay one more parcel per
  global access, using 1b's 32-bit absolute mode.

## Caveats

- **The timing model**, not the microcode, costs everything: D32-separate,
  as in [timing-model-v1.md](../studies/v1_isa/timing-model-v1.md). Only
  the tagged mode needed a guess about the microcode, given both ways.
- **The what-if costings ignore second-order effects:** code size,
  branches that would now reach, a register given up.
- **The benchmarks are small**, and the collector's share depends on the
  heap size.
- **The compiler is simple.** With register allocation the absolute
  savings stay about the same, but they'd be a larger share of a smaller
  total.

## Appendix: v1bx, draft 1b with a tagged register mode

An experiment, not a proposal for draft 1b as it stands: draft 1b plus
one addressing mode, to measure what checking integer tags in hardware
is worth to the Lisp ([The tagged register mode](#the-tagged-register-mode)).

Everything not mentioned here is draft 1b
([RFC 0004, Part II](0004-rfc-draft-1-isa.md#part-ii-draft-1b)). The
instruction-level simulator runs it as the ISA `v1bx`
(`studies/v1_isa/isa`, `Isa::V1bx`). The runtime is assembled as 1b and
doesn't use the new mode; the compiler writes it when it's built with the
feature `tagged` (`heron lisp run -c --features tagged`,
`heron lisp test -c --features tagged`).

### Mode E: a tagged register

Draft 1b reserves mode E. In v1bx it is the register `R`, as mode 0, with
a check that both operands are integers in the Lisp's representation
(bit 0 clear):

| Instruction | Does | Traps if |
|---|---|---|
| `MOV.T rd, rs` (`1 d E s`) | `rd ← rs`, sets N and Z | bit 0 of `rs` is set |
| `ADD.T rd, rs` (`4 d E s`) | `rd ← rd + rs`, flags as `ADD` | bit 0 of `rd` or `rs` is set, or the sum overflows |
| `SUB.T rd, rs` (`5 d E s`) | `rd ← rd − rs`, flags as `SUB` | as `ADD.T` |
| `CMP.T rd, rs` (`6 d E s`) | flags of `rd − rs` | bit 0 of `rd` or `rs` is set |
| `AND.T`, `OR.T`, `XOR.T` (`7`–`9 d E s`) | as the plain operation | bit 0 of `rd` or `rs` is set |

`ST`, `LEA`, `JMP` and `CALL` with mode E are illegal instructions, as in
1b. `r0` reads as zero, which is an integer, so `CMP.T r1, r0` checks `r1`
and compares it with 0 (the compiler's `zero?`), and `MOV.T r9, r1` only
checks `r1`.

The trap goes through a new vector, **`0x18`** (after the address error
at `0x14`). It's taken before anything is written, like an address error:
the saved PC is the instruction's own address, and the flags and the
registers are as they were. The handler decodes the instruction to tell
the two cases apart and to find the irritant (`trap_tag` in
[rt/start.s](../studies/lisp/rt/start.s)): if both operands are integers,
an `ADD` or `SUB` overflowed.

### What the compiler does with it

Without the mode, `(+ a b)` on two values in `r1` and `r3` is

```
        MOV  r9, r1             ; r1 an integer?
        AND  r9, #1
        BNE  not_a_number
        MOV  r9, r3             ; r3 an integer?
        AND  r9, #1
        BNE  not_a_number
        ADD  r1, r3
        BVS  overflow
```

and with it, `ADD.T r1, r3`. `(< a b)` becomes `CMP.T r1, r3` and a
branch, `(zero? a)` `CMP.T r1, r0`, and checking one operand (a vector
index, `(- a)`) `MOV.T r9, r1`.

### What it would cost

Not designed in hardware. On the 1b data path the check is an OR of bit 0
of the A and B buses (the B bus alone for `MOV`), and with the ALU's
overflow for `ADD` and `SUB`. The microcode's 3-bit condition field
(`COND`, [report 0012](0012-report-draft-1b-hardware.md#5-control)) is
full, so the check would go through the condition latch, which has a
spare source. That is about one chip of gates. A register ALU operation
writes its result in its second cycle, together with the next fetch;
checking before the write probably needs one more cycle, which
[The tagged register mode](#the-tagged-register-mode) counts both ways.
