# Report 0017: An object language on draft 1b, interpreted and compiled on the machine

What a dynamic object language costs on draft 1b, where the cycles go,
and which changes to the instruction set or the system would help it. The
language is Egret ([studies/egret](../studies/egret/README.md),
[language.md](../studies/egret/language.md)), made up for the study: a
small Smalltalk with Ruby's syntax, where everything is an object and
every operation a message send, with closures, non-local return, and
integers that grow into big integers. The per-program tables are in
[performance.md](0017-report-egret/performance.md), generated by
`heron egret bench --write`.

In short:

- **It works on the machine.** The VM compiles Egret source to bytecode
  and runs it, all on draft 1b, with a 408-line prelude compiled at every
  start (4.9M cycles, 1.6 s at 3 MHz). A template JIT, also on the
  machine, compiles bytecode to 1b code as methods are first called.
- **It's slow, in the usual way.** With the hand-written interpreter loop,
  Egret takes 18× the cycles of the same programs in compiled C and 32×
  hand-written assembly (geometric means, D32-separate). The JIT gets
  1.5× over the interpreter on the long runs (1.0–1.85×) but loses on
  short ones, where compiling costs more than it saves.
- **No instruction is worth much to the interpreter.** Its cycles are
  spread over dispatch (19%), sends (21%), pushes and stores (16%) and
  arithmetic (14%); tagged arithmetic would save 2–3%, everything else
  measured about 1% or less. Dispatch is the one big item, and it's
  software: direct threading would save 11%.
- **Compiled code changes that.** Without dispatch, the SmallInt tag
  tests are what's left in the arithmetic: add, subtract and compare that
  trap on a non-SmallInt would save 5.5% of the JIT's runs on average, and
  16–18% of the numeric ones (life, mandel). That's the one ISA change
  this study supports.
- **The rest is the run-time's design,** not the instruction set: a call
  and return cost about 135 cycles in compiled code, and nearly half of
  the native cycles touch the value stack or the frames.

## The VM

Written for the study, in C, so the C compiler study could build it for
1b; gcc builds the same source for the host, which is how the programs
were first checked.

- **Values** are 32 bits. SmallInts are tagged (2n + 1); everything else
  is a pointer to an object with a two-word header (class; size, hash and
  format). `nil`, `false` and `true` are objects at fixed low addresses,
  so `FALSY(v)` is `(v | 8) == nil`.
- **Memory:** a permanent space (classes, methods, symbols, literals, and
  the JIT's code), never collected, and two 256 KB semispaces with a
  Cheney collector. The 1 MB map: image below 0x30000, console input, 160
  KB permanent space, a scratch area for the compiler, the value stack and
  the frame stack, the semispaces, the C stack.
- **Execution:** bytecode for a stack machine, with frames on a frame
  stack of their own and arguments and locals on the value stack. Sends go
  through a global method cache of 1,024 entries; `+`, `<`, `[]` and the
  others have bytecodes with SmallInt fast paths. Blocks copy the
  variables they capture, or share a box when someone assigns them; a
  non-local return finds its home frame by address and checks a serial
  number. Big integers, strings, lists and maps are C primitives.
- **The compiler** is a recursive descent parser into a tree per method,
  then bytecode; about 2,200 lines of C with the lexer.

Three builds of the VM run the same programs to the same output:

| Build | The interpreter loop | Image |
|---|---|---:|
| interpreter | by hand, 980 lines of 1b assembly (`interp_v1b.s`), with the C loop as its slow path for the rare bytecodes | 140 KB |
| C loop | `interpret()` in C, compiled by the C compiler | 138 KB |
| JIT | none: methods compiled to 1b code when first called (`jit.c`, 1,400 lines), anything else run by the C loop one bytecode at a time | 184 KB |

The programs are twelve of the draft 1 suite's, written the way an Egret
programmer would (with blocks, ranges and collections, not arrays of
bytes), plus five of Egret's own:
Richards, binary trees, a JSON writer and parser, shapes (sends to six
classes at one site) and closures. Their output matches the suite's
expected output, so the cycle counts compare with the C and assembly
versions.

## What it costs

Geometric means over the programs, of each program's run after start-up
and after compiling its source:

| Configuration | interpreter / C | interpreter / assembly | C loop / interpreter | interpreter / JIT | JIT / C |
|---|---:|---:|---:|---:|---:|
| D16-overlap | 17.1 | 29.6 | 1.74 | 1.08 | 17.8 |
| D32-separate | 18.4 | 31.9 | 1.74 | 1.07 | 19.2 |
| D32-wide | 17.5 | 29.6 | 1.70 | 1.14 | 17.3 |

- **Against C,** the interpreter is 10–45× on the suite's programs
  (bignum, 2.5×, is mostly big integer code in C either way).
- **The C loop takes 1.74× the hand-written one's cycles.** The C
  compiler keeps the VM's registers in registers, but its dispatch is 6
  instructions against 2 (a bounds check on the opcode, the table's
  address loaded each time, and one shared dispatch that every handler
  jumps back to), and C has no overflow flag: its `ADD` works out with
  XORs and an AND what the assembly gets from `BVS`.
- **Start-up** is 4.9M cycles, 1.6 s at 3 MHz: compiling the prelude, 36
  KB of permanent space. Compiling a program's own source costs up to
  3.9M cycles; Richards' 300 lines take 1.3 s.

### Where the interpreter's cycles go

Means over the programs, D32-separate (per program in
[performance.md](0017-report-egret/performance.md#where-the-interpreters-cycles-go-d32-separate--of-each-programs-run)):

| | % |
|---|---:|
| dispatch (`MOV r1, byte [r8]+` / `JMP [r13 + r1*4]`) | 19 |
| sends: the method cache, frames, returns, primitive calls | 21 |
| pushes and stores | 16 |
| arithmetic and compares | 14 |
| `[]` and `[]=` | 4 |
| jumps and loops | 6 |
| C: the slow path, primitives, allocation, big integers, maps | 21 |

Send-heavy programs (Richards, binary trees, bst, queens) spend 35–45%
in sends; loop-heavy ones (sieve, mandel, life) 25–30% in dispatch.

## ISA changes for the interpreter

The hand-written loop marks the instruction sequences a new instruction
would replace (`;@tag2` … `;@end`). From a run, each sequence's executions
and cycles come straight from the simulator, and what it would cost
instead is the timing model's cost of instructions with the same work
(`isa.py`). Percentages of each program's run, mean and maximum over the
programs, D32-separate:

| Change | What | mean | max |
|---|---|---:|---:|
| TTST | tag test of two registers: Z unless both are SmallInts | 2.2 | 5.8 (mandel) |
| TADD/TSUB | SmallInt add and subtract that trap on a non-SmallInt or overflow (SPARC's `TADDccTV`) | 1.8 | 10.2 (life) |
| TCMP | compare that traps on a non-SmallInt | 0.9 | 3.3 (mandel) |
| LDCLASS | load a value's class: a register for SmallInts, the word it points at otherwise | 0.5 | 1.1 |
| XOR3 | three-operand XOR, for the method cache's hash | 0.4 | 0.9 |
| LDH unaligned | a 16-bit load at any alignment, for jump offsets | 1.1 | 2.2 |
| direct threading | (software) code of handler addresses, `JMP [r8]+` | 11.4 | 18.0 (sieve) |

- **Each instruction saves a cycle or two of a 30–60-cycle bytecode.** The
  loop is already short: a send and its return are 44 instructions, an
  `ADD` 12 with its dispatch. The tagged operations do best, in the
  integer loops of life and mandel; the trapping forms cost a trap
  whenever an operand isn't a SmallInt, which the numbers include (with
  20 cycles to find the slow path).
- **Dispatch is the largest single item,** and 1b can already do better:
  direct-threaded code (`JMP [r8]+` through a list of handler addresses)
  saves 10–18% where the interpreter's own cycles dominate, 3–9% where C
  does (bignum, json, matmul). It costs 4 bytes per bytecode instead of
  1, and the compiler's jumps and operands would have to change, so it
  wasn't built.
- **The loop leans on 1b's addressing.** In Richards, sieve and json,
  auto-increment loads and stores (the value stack, fetching bytecode)
  are 21–37% of the loop's executed instructions, `JMP [r + r*4]` 7–14%,
  indexed loads and stores 4–8%. A 1b-based draft 2 keeps them; a
  1a-based one would want the auto-increment forms and the table jump
  that [RFC 0006](0006-rfc-ideas-isa.md#4-if-draft-2-builds-on-1a-after-all)
  lists for it.

## Compiling on the machine

The JIT is a template compiler, in the style of V8's Sparkplug: one
template per bytecode, the same value stack and frames as the
interpreter, so C can take over at any bytecode.

- **Sends** have a monomorphic inline cache: compare the receiver's
  class with a constant, call a constant address. A miss binds the site;
  a site bound three times goes megamorphic and calls a stub that probes
  the global method cache. Calls go straight into the callee's native
  code, a C primitive's stub, or stubs for blocks and `new`.
- **Operators** have their SmallInt fast path inline; when it fails, they
  send through the method cache, as the interpreter does (so `==` on
  strings, and `[]` on strings and maps, stay out of C).
- **Fusion:** a compare and the conditional jump after it make one
  compare-and-branch; `x + 1`, `x < 10` and `x == nil` take their
  constant as an immediate.
- **Slow paths** (stack overflow, and the bytecodes it doesn't compile:
  building lists, maps and strings, setting up loops, `try`, non-local
  return) go to the C loop for one bytecode, then back to native code
  through each method's map from bytecode to native address.

The code goes into the permanent space; Richards' 69 compiled methods
are 23 KB of it.

### What it gains

| | interpreter / JIT |
|---|---:|
| the 12 programs whose run takes the interpreter more than 5M cycles (geometric mean) | 1.50 |
| fib, Richards, sieve, binary trees, mandel, crc | 1.63–1.85 |
| shapes (megamorphic), wordfreq and json (C primitives) | 1.00–1.34 |
| bignum, bst, matmul, hello (short) | 0.06–0.88 |

- **Compiling is slow:** 1,050–1,400 cycles per byte of bytecode, and the
  code is 14–20× the bytecode's size. A 100-byte method takes 0.04 s at
  3 MHz to compile. In bst, matmul and bignum that's 35–46% of the run,
  and the JIT loses. A JIT for this machine has to be mixed-mode:
  interpret first, compile what runs often.
- **The wide bus helps it most** (1.14× against 1.07× on D32-separate):
  native code is mostly loads and stores of the value stack and frames,
  which the 32-bit bus makes one cycle.
- **What cost the most before it was fixed:** operators whose fast path
  failed went to C for the bytecode (json's string compares were 39,000
  of its 58,000 trips to C, which took 29% of its run); polymorphic sites
  rebinding their cache on every miss (shapes, 11%); a 57-cycle function
  call for every halfword of code emitted (`put` was 37% of compiling).

### Where the JIT's cycles go

Native code is 70–90% of most long runs (40–50% of json's and
wordfreq's, which live in C primitives). In the send-heavy programs calls
are the biggest single item, and in all of them nearly half the native
cycles touch the value stack or the frames (a third the value stack
alone, on average):

| | Richards | fib | trees | mandel | life |
|---|---:|---:|---:|---:|---:|
| calls: inline cache, prologue, return, % of the run | 50 | 37 | 44 | 2 | 0 |
| native cycles touching the value stack (r9, r10), % | 31 | 34 | 26 | 47 | 44 |
| native cycles touching frames (r11, sp), % | 24 | 21 | 26 | 1 | 0 |

A send and return is about 135 cycles of native code on D32-separate
(122 on D16-overlap): the inline cache (9 instructions, 38 cycles), the
prologue (13 instructions, 60 cycles: the return address into the frame,
five more stores, a stack check; for locals another check and a nil
each) and the return (8 instructions, 37 cycles). Of the six words a
frame holds, native code reads three: bp, where to go on, and the flags
(for `new`, and the frame C called into). The bytecode address and the
method are for C, the serial for non-local return.

## Changes for compiled code

Estimated the same way, but the JIT's code isn't marked: `isa.py` finds
the templates' instruction sequences in the disassembly of what ran.
Percentages of each program's run with the JIT, D32-separate:

| Change | Kind | What | mean | max |
|---|---|---|---:|---:|
| TADD/TSUB/TCMP | ISA | add, subtract and compare that trap unless both operands are SmallInts (and the sum fits) | 5.5 | 17.5 (mandel) |
| TTST | ISA | tag test of two registers | 2.7 | 10.1 (mandel) |
| LDCLASS | ISA | load a value's class, in every inline cache | 1.0 | 2.8 (queens) |
| BL | ISA | a call that leaves the return address in a register, not on the stack | 0.7 | 2.6 (Richards) |
| CHK | ISA | compare with a bound and trap (68000 `CHK`): the prologue's stack checks without their branches | 0.3 | 1.3 (Richards) |
| one stack check | system | frames and values in one region, growing towards each other: one register compare | 0.1 | 0.8 |
| no bytecode ip | software | C finds a native frame's bytecode from its return address: no `MOV r8, #ip` per send, no store in the prologue | 1.1 | 3.3 (Richards) |

- **Tagged arithmetic doubles in value** once dispatch is gone. A native
  `ADD` is two pops, a 4-instruction tag test, the untagging `DEC`, the
  add, the overflow branch and a push; with a trapping `TADD` it's the
  pops, the add and the push. The numeric programs save a sixth of their
  cycles. For the interpreter the same instructions are worth half as
  much on average, a third as much in mandel.
- **The call instructions don't matter much:** the calls are long because
  of what they store, not the call and return themselves. `BL` saves a
  push and a pop per call, 2–3% at most.
- **What would matter is software:** keeping the top of the stack and
  the locals in registers (a third of the native cycles are value-stack
  traffic), smaller frames, and compiling only what runs often. None of
  them needs a new instruction.

## The system

- **Memory:** the prelude and a program fill 50–57 KB of the permanent
  space; the JIT adds 32–37 KB of code and inline caches. Garbage was no
  problem with 2 × 256 KB semispaces: binary trees, the allocation-heavy
  one, spends 3% in the collector and 7% allocating. The 1 MB map was
  enough, but the JIT build's image ends 8 KB below the console buffer.
- **31-bit SmallInts** turn matmul's 32-bit checksum into a big integer,
  which is 36% of its run (bignum's numbers are big by design).
- **Code addresses:** the JIT calls with 32-bit absolute addresses (3
  parcels) because native code in the permanent space is more than 64 KB
  from the glue and the C code, out of reach of 1b's PC-relative calls.
  Inline caches compare against 32-bit class constants, also 3 parcels.
  1b's short constants don't help a JIT, which deals in addresses.
- **The C compiler** had two bugs the VM met (switch tables addressed
  with 16 bits once the code passes 32 KB; `extern T a[]` sized from the
  declaration), worked around in the study.

## What this suggests

- **Tagged add, subtract and compare that trap,** if draft 2 is meant to
  run compiled dynamic languages well: 5.5% on average, a sixth of the
  numeric programs. They cost an opcode or a mode and a trap vector.
  For an interpreter alone they're worth 2–3%.
- **Keep auto-increment and the table jump** in draft 2 (1b has them;
  1a would need them added); an interpreter uses them on every bytecode.
- **Not worth an instruction:** a class load, a three-operand XOR,
  unaligned 16-bit loads, a link-register call, a bounds-check trap. Each
  saves about 1% or less on average, interpreted or compiled.
- **For the language itself,** the next steps are software: direct
  threading for the interpreter (11%), and for the JIT, compiling only
  what runs often and keeping values in registers.
