# Report 0011: The C compiler's code, and 1a against 1b for compiled code

How the code the C compiler ([compiler.md](../../studies/c_compiler/compiler.md)) makes compares with
the hand-written draft 1 programs, and what that says about the choice
between 1a and 1b. The per-program tables are in
[performance.md](performance.md), generated by
`heron c_compiler bench --write`.

## Compiled C against hand-written assembly

The 15 programs in `programs/c/` are C versions of the hand-written
programs of the same name. They print the same output (checked against
`programs/expected/`) and use the same algorithms where C can express them;
`bignum` keeps its number in base 10⁴ because C has no 64-bit type. They
use `printf` where the assembly versions call their own print routines.
The other five draft 1 programs have no C version: `interrupts` needs
interrupt handlers, which can't be written in C yet, and `lines`,
`monitor`, `rpn` and `vm` just haven't been ported.

Cycles on D16-overlap, compiled C relative to the hand-written assembly
(geometric means; per-program tables in
[compiler-performance.md](performance.md)):

| | 1a | 1b |
|---|---:|---:|
| Whole programs | 1.83 | 1.87 |
| The program's own code, without the C library | 1.22 | 1.22 |

The second row leaves out programs that spend more than half their time in
the C library (arith, bignum, hello, strings), which mostly measure printf.

- The closest are matmul, life, sieve, fib and queens (1.03–1.13×), where
  the hot loops come out much as a person would write them.
- The furthest are sort, bst, wordfreq and crc (1.3–1.6×), and bignum
  (1.6×, with its different number representation). The assembly versions
  keep values in registers that the compiler reloads or saves: `a[j - 1]`
  of one iteration is `a[j]` of the next, and fib and bst save and restore
  callee-saved registers on every call, even the half that return at once.
- printf costs about 3× the assembly programs' own print routines; it
  parses the format string at run time and handles every option.

## 1a against 1b for compiled code

| | asm: 1b / 1a | C: 1b / 1a |
|---|---:|---:|
| D16-overlap | 0.925 | 0.943 |
| D32-overlap | 0.936 | 0.950 |
| D32-wide | 0.921 | 0.938 |

The asm column covers the 15 programs that have C versions, so it differs a
little from the means over all 20 programs in
[evaluation-v1.md](../0004-report-draft-1-evaluation/README.md) (0.919, 0.932 and 0.915).

The [draft 1 evaluation](../0004-report-draft-1-evaluation/README.md) expected compiled code to favour
1b more than hand-written code, through stack frames and memory operands.
It's the other way round here:

- **Auto-increment still pays,** when strength reduction turns an array
  loop into a pointer walk (`MOV r5, [r1]+` in `dot` in [compiler.md](../../studies/c_compiler/compiler.md#what-the-code-looks-like), `ST r4, byte
  [r3]+` in `copy`; sieve, sort and life take 0.84–0.87× of their 1a
  cycles on 1b). It mostly appears in loops that step one pointer by the
  access size.
- **Memory operands are used, but save little:** 30% of the compiled 1b
  code's ALU instructions take a memory operand (41% in the hand-written
  code), and each saves only one cycle over a load and an ALU instruction.
- **Stack frames barely show up.** The register allocator keeps nearly
  everything in registers, so `[sp + n]` is 0.1% of the operands.
- **The 4-bit constants cost the compiler more than a person:** 5.6% of
  compiled 1b operands are 16- or 32-bit constants against 1.0% in the
  hand-written code. Character tests (`c >= 'a'`), masks and hash
  multipliers all need an extension parcel, or a register (and so a
  callee-saved register across calls). Three of the fifteen programs
  (bignum, bst and queens) come out a fraction slower on 1b than on 1a.

So for a compiler, 1b's lead shrinks (6% rather than 7.5%), and its 4-bit
constants weigh more heavily. That supports the evaluation's recommendation:
1a with auto-increment loads and stores would keep most of what the compiler
gets from 1b.
