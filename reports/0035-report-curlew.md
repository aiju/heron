# Report 0035: Curlew: a lazy, typed language on draft 2

Curlew is a small lazy functional language with Hindley–Milner types and
type classes, in the spirit of Haskell and Miranda, made to see what lazy
evaluation asks of draft 2 ([RFC 0028](0028-rfc-draft-2-isa.md)): in
particular whether the tagged operations, which the Lisp put into the
draft for its type checks, serve a language whose checks are for
evaluation. The study is [studies/curlew](../studies/curlew/README.md):
a compiler in Python on the host, after the STG machine with pointer
tagging, and a runtime in draft 2 assembly, run on the draft 2
instruction-level simulator.

Cycles are the timing model's for D32-separate, the configuration of the
built 1b hardware ([report 0012](0012-report-draft-1b-hardware.md)), with
draft 2 costed as if it were built the same way; the other configurations
move the tagged run's cost by at most 3.3 points (5.8 in `life`).
Changes are geometric means over the 14 benchmarks. The per-program
tables are generated by `heron curlew report --write` into
[performance.md](0035-report-curlew/performance.md), which follows the
code.

## Summary

- **Curlew works:** 14 benchmarks and 14 tests pass against a reference
  interpreter, as built and with every experiment switched on. A typed,
  lazy `tak` takes 4.0M cycles, where the compiled Lisp takes 8.5M
  ([below](#compared-with-the-lisp)).
- **Laziness costs about a third of the cycles** in the median program:
  6% in the evaluation checks, 17% in evaluating what they find
  unevaluated, 14% in thunks' entry and update. Allocation takes another
  14%.
- **The tagged operations as evaluation checks lose 28%.** `TTST r, r`
  traps when bit 0 is set, which in Curlew means "not evaluated yet". But
  the checks find an unevaluated value 33% to 99% of the time, half of
  them in the median program: the "exception" is the common case. A trap
  costs at least 56 cycles more than the branch it replaces, though the
  handler jumps straight to the check's own slow path, so a check gains
  only where fewer than 4–5% of its runs trap. With a handler that cost
  nothing they would still lose 4.5%.
- **As arithmetic they help a little:** `TADD` and `TSUB` are an add and
  subtract that trap on overflow, which Curlew's 30-bit `Int` wants:
  −0.4%, and −2.8% in `nfib`. Their tag check is redundant in a typed
  language, and harmless.
- **The tag fits:** bit 0 clear is "an integer" to the Lisp and "evaluated"
  to Curlew, with `Int`s as 4n. One test serves both.
- **A branch on the tag would work better than a trap:** a two-parcel
  branch on bit 0 saves 1.9%, a one-parcel `TST r, #q` 1.0% (and keeping
  1 in a register measures 0.9%), a `MOVS` that sets C from bit 0 0.8%.
- **Elsewhere:** stack-limit checks take 4.6% (8.5% in `nfib`), which a
  guard page under RFC 0029's page map would take away; storing a
  constant without a register (2.7%) and one-parcel loads at small
  offsets from a tagged pointer (2.9%) are worth more than the branch on
  the tag.
- **Draft 2 fits a lazy language well:** mode E, `[r14 + 4R]`, fills new
  objects (5–10% of the instructions in most programs; the Lisp found no
  use for it), the link register and `SAVE` ranges make thunks and calls
  cheap, and `CALL [r6 - 1]` enters an object through its header because
  `CALL` clears bit 0.
- **The compiler matters most:** without strictness analysis the programs
  take 53% more cycles, without inlining 106%, without specialisation 15%
  (185% in `wordfreq`).
- **The proposals** are in [RFC 0006, section 6](0006-rfc-ideas-isa.md#6-for-dynamic-languages),
  with the Lisp's and Egret's.

## Curlew

The language ([language.md](../studies/curlew/language.md)) is a small
Haskell 98: layout, pattern matching with guards, `where`, list
comprehensions, `do`, user-defined operators, algebraic data types with
`deriving`, single-parameter type classes with superclasses and defaults
(`Eq`, `Ord`, `Show`, `Enum`, `Functor`, `Monad`), strict fields and
bang patterns. It departs from Haskell where that keeps it small: a
program is `main :: String -> String`, a function from the input to the
output, both lazy, as in Miranda; `Int` is the one number type, of 30
bits, and overflow is an error; arithmetic isn't overloaded.

The compiler ([implementation.md](../studies/curlew/implementation.md))
infers types, compiles patterns and passes dictionaries, optimises a
small core language (inlining, specialisation, case of case, join
points, lambda lifting, strictness analysis) and generates draft 2 code
from an STG-like form. A value is a word with a two-bit tag: `00` an
immediate (an `Int` or `Char` as 4n, a constructor without fields), `10`
a pointer + 2 to an evaluated object, `01` a pointer + 1 to one that may
not be evaluated, `11` an object's header. So **bit 0 set means "not
evaluated yet"**, and a check before a value's use is `TST r, #1` and a
branch to an out-of-line slow path, which follows an indirection or
enters the thunk.

The benchmarks are 14 small programs that use laziness in the usual
ways: infinite lists (`primes`, `hamming`, `edigits`), lazy trees
(`trees`, `sort`, `wordfreq`), symbolic code (`deriv`, `parser`, `peano`),
a state monad written from scratch (`state`), lists of lists (`life`,
`queens`), and the strict cases (`nfib`, `tak`).

## Where the cycles go

In the median program
([table](0035-report-curlew/performance.md#where-the-cycles-go)):

| | Share |
|---|---:|
| evaluation checks (`TST`, `BNE`) | 6% |
| slow paths: following an indirection or entering a thunk | 17% |
| thunks: entry, the free variables' loads, the update | 14% |
| allocation | 14% |
| known calls and returns, with their saves | 12% |
| case and fields | 9% |
| arithmetic | 5% |
| stack checks | 5% |
| the collector | 2% |
| unknown calls | 2% |
| heap checks | 1% |

The machinery of laziness (checks, slow paths, thunks) takes 27–53% of
the cycles in the lazy programs, 11% in `tak`, where the strictness
analysis turns everything but its list version into call-by-value code,
and nothing in `nfib`.

Programs run 1.6 to 6.2 evaluation checks per 100 instructions
([table](0035-report-curlew/performance.md#evaluation-checks)), and
**33% to 99% of the checks find a value not yet evaluated**: half in
`trees`, `hamming` and `life`, 91% in `edigits`, whose stream of digits
is rebuilt lazily for each digit. Of those, 0% (`trees`) to 97% (`tak`'s
list version) are indirections: thunks already evaluated, reached
through a pointer made before. The checks cluster at sites that almost
never find a thunk (below 0.1% of the time: up to 55% of a program's
checks) and at sites that find one at least one time in ten (the rest,
nearly all); only `primes` and `sort` have many checks in between.

## The tagged operations

### As evaluation checks

With the feature `tagged`, every evaluation check is `TTST r, r`, which
traps when bit 0 of `r` is set. To give the trap its best case, the
handler doesn't evaluate in general: it looks the trapping instruction's
address up in a hash table, which start-up fills from the compiler's list
of checks, and jumps to that check's own slow path, the same one the
branch would have taken, which knows what's live and ends with `RTI` to
run the check again. A check that doesn't trap costs 2 cycles where
`TST r, #1` and `BNE` cost 5.

| | Geomean | Range |
|---|---:|---:|
| Trapping checks (against `TADD` and friends alone) | +28% | +16% (`state`) to +54% (`edigits`); none in `nfib` |
| Cycles a trap costs beyond taking the branch | | 56 to 80 |
| …in the handler's lookup | | 41 to 65 |
| Break-even: the share of a site's checks that may trap | | 3.8% to 5.4% |
| Trapping only at the sites below the break-even (a perfect profile) | −0.9% | 0 to −2.1% |
| A handler that costs nothing | +4.5% | +2.2% to +9.6% |
| A branch on bit 0 instead (below) | −1.9% | 0 to −3.7% |

([Table](0035-report-curlew/performance.md#the-tag-trap-as-an-evaluation-check).)
Of a trap's 56 cycles at best, 15 are the machine's (entering the
exception, the vector's jump, `RTI` and the check again) and 41 the
lookup; collisions in the hash table take it to 80 in `sort`. A check
saves 3 cycles when it doesn't trap, so it gains where fewer than about
one in twenty of its runs trap, and every program has most of its checks
at sites that trap far more often than that. With the profile of the
very run, trapping at only the cold sites would save up to 2.1%, less
than the branch saves everywhere without one.

So the trap is the wrong tool for evaluation: it's built for checks that
almost never fail, like the Lisp's type checks, whose failure is an
error. A lazy program's checks fail all the time, by design. On a system
with RFC 0029's protection the case is weaker still: the tag trap enters
supervisor mode, so a program running in user mode would need the kernel
to pass every trap back to it. (The Lisp's errors, being rare, don't
mind; nor do Curlew's overflows.)

### As arithmetic

`TADD` and `TSUB` trap on overflow, and Curlew's `Int` is 30 bits whose
overflow is an error: they replace `ADD` and `BVS` (feature `tagarith`).
That saves 0.4% (−2.8% in `nfib`, −1.2% in `trees`), the branch after
each add and subtract. Their tag check never fires in a typed language,
since the compiler only adds integers; it's harmless. `TCMP` gives
nothing (a compare can't overflow) and `TMOV` has no use.

### The tag

The tagged operations take bit 0 clear as "an integer"
([RFC 0028, open question 5](0028-rfc-draft-2-isa.md#12-open-questions)).
For Curlew that is "evaluated", with `Int` as 4n, evaluated pointers at
+2 and unevaluated ones at +1: the one test serves a dynamic language's
type check and a lazy language's evaluation check. With Egret's 2n + 1
the operations would trap on bit 0 clear, Curlew's evaluated values;
Curlew could flip its tags to match, so the choice matters less to it
than to the Lisp and Egret. A register holding the expected tag, as RFC
0028 suggests, would serve all three.

### What would work better

A check whose outcome is often "go the other way" wants a branch, and the
trouble with `TST r, #1` and `BNE` is only that it is two instructions,
the first of two parcels. What each alternative would save
([table](0035-report-curlew/performance.md#what-other-changes-would-save)):

| Change | Geomean | Range |
|---|---:|---:|
| A branch on bit 0, two parcels, costed like `JNE` (3 cycles where `TST` and `BNE` take 5) | −1.9% | 0 to −3.7% |
| A one-parcel `TST r, #q` (2 cycles where `TST r, #1` takes 3) | −1.0% | 0 to −1.9% |
| …measured: `TST r, r11` with `r11` kept at 1 (feature `onereg`) | −0.9% | 0 to −1.7% |
| `MOVS` setting C to bit 0, so a check right after a load is just `BCS` | −0.8% | 0 to −2.1% |

The measured `onereg` comes within 0.1 points of the estimate for a
one-parcel `TST`, so losing `r11` to the constant costs almost nothing; a
compiler can do that today. A branch on a bit could be general:
`BBS r, #b, label` and `BBC`, branch if bit b (0–15) of r is set or
clear, the register and the bit in the register byte and a 16-bit
offset, in two of the free root cells (`F9`–`FB`). Bit 0 would serve
Curlew's checks, and other bits the Lisp's type bits, the kernel's
bitmaps and flag words. The Lisp would keep `TTST` for checks that fail
only on errors, where 2 cycles beat 3.

The sign bit as the mark instead of bit 0 (so that the load before a
check sets N) loses 2.0%: setting the mark on every thunk made and
clearing it on every one evaluated costs more than the `TST`s it saves.

## Other changes

| Change | Geomean | Range |
|---|---:|---:|
| A guard page below the stack: no stack checks (measured) | −4.6% | −1.0% to −8.5% |
| One-parcel `[R + d]` at small offsets from a tagged pointer | −2.9% | 0 to −4.7% |
| Storing a constant without loading it into `r12` | −2.7% (at most) | 0 to −4.5% |
| A guard page above the allocation area: no heap checks | −1.2% | 0 to −2.2% |

- **The stack checks** are `CMP sp, [stack_limit]` and `BLO`, 8 cycles,
  once on each path that calls. RFC 0029's page map gives a guard page
  for nothing, and since running out of stack is fatal in Curlew, the
  kernel need only stop the program: no handler in user mode. Keeping the
  limit in a register would take half the cost away, for a register.
- **Fields** are at 4k − 2 from a pointer tagged + 2 (and 4k − 1 from one
  tagged + 1), as with the Lisp's tagged pointers, so they need
  `[R + d16]`, two parcels; RFC 0028's
  [section 10.1](0028-rfc-draft-2-isa.md#101-short-offsets) leaves short
  offsets to mode E, which can't express them. A one-parcel mode that
  reached a few words around a tagged pointer would serve both languages.
- **Constants** stored into new objects are mostly headers (a thunk's or
  a constructor's code address + 1) and small integers; each is
  `MOV r12, #c` and a store. The figure counts the whole `MOV`, so it is
  an upper bound.
- **The heap checks** are cheap already: one check covers the allocations
  that follow it on a path, up to 1 KB. A guard page here would also need
  the fault to restart into the collector, from user mode under an OS.

## What draft 2 already does well

- **Mode E** stores the fields of new objects at `[r14 + 4R]`, `r14` being
  the allocation pointer: 5–10% of the instructions in the lazy programs
  but `life`. Report 0032 found no use for it in the Lisp.
- **The link register** lets a function that only calls on slow paths
  return with `RET`, untouched by memory; a thunk's update frame is
  `SAVE r6-r7`, the node and the return address in one instruction, and a
  thunk's tail call sets `r7` to the update and jumps.
- **`SAVE` ranges next to `r7`:** variables live across calls are given
  the registers next to `r7`, so that most saves are one `SAVE` of 2–3
  registers with the return address (report 0033 did the same for the
  Lisp's arguments). Where a range would hold dead registers, pushes are
  cheaper; a dead register inside a range gets its slot cleared (`CLR`)
  so that the collector sees no stale pointer.
- **`CALL` and `JMP` clearing bit 0** make an object's header word both
  its code address and recognisable: the header is the entry + 1, with tag
  `11`, which no value has, so the collector tells a headerless pair from
  an object with a header; `CALL [r6 - 1]` enters a thunk through it.
- **`INC rd, rs`** makes a thunk's pointer `r14 + 1` in one parcel, and
  `LEA` the others; `CLR` stores the zeros.
- **Unused:** `LDM` and `STM` (only in the general apply's rare paths),
  and the tentative instructions other than the tagged ones.

## Compared with the Lisp

`tak` is the one benchmark the Lisp and Curlew share, line for line (with
TAKL after it). Curlew takes 4.04M cycles for the whole run; the compiled
Lisp takes 8.49M on draft 2 for its compiled forms alone, 7.60M with the
tagged operations ([lisp.md](0032-report-lisp-egret-draft-2/lisp.md)).
The types make the difference: Curlew's `tak` needs no type checks, and
its strictness analysis passes the integers evaluated, in registers,
where the Lisp checks each operand's tag. The list version keeps its
laziness, and most of the 1.6 evaluation checks per 100 instructions are
there.

## The compiler matters more than the instruction set

([Table](0035-report-curlew/performance.md#the-configurations).)

| Without | Geomean | Range |
|---|---:|---:|
| strictness analysis | +53% | +0.8% (`edigits`) to +312% (`tak`) |
| specialisation (dictionaries passed at run time) | +15% | 0 to +185% (`wordfreq`) |
| inlining | +106% | +3% to +611% |
| following indirections inline (entering them instead) | +2.0% | −4.5% to +24% |
| a thunk's tail call going straight to the update | 0% | −0.5% to +1.1% |

Every change to the instruction set above is worth a few percent; each of
the optimiser's passes is worth tens. The measurements also made the
compiler better on the way: one stack check per path instead of one per
call (`nfib` −8%), allocations sharing a heap check, `ap_N` entering a
partial application that the call completes (it took the general apply
500 cycles), and a method of an instance with a context specialised where
it's called (`life` −40% for the last two). What it still leaves:

- `life`'s checks find an indirection 96% of the time: the same field
  forced again and again. Writing the evaluated value back into the field
  that held the thunk would take most of those slow paths away.
- `parser` and `wordfreq` spend 11–12% in unknown calls, the higher-order
  functions they pass around.
- The allocations on a path each bump `r14`; one bump would do.

## Open questions

- **For RFC 0028:** whether a lazy language's evaluation check is worth an
  instruction: a branch on a bit (−1.9%), a one-parcel `TST` with a quick
  constant (−1.0%, and nearly all of it available today by keeping 1 in a
  register), or a `MOVS` that sets C from bit 0 (−0.8%, no new cell). And
  whether the tagged operations' trap should go to a user-mode handler;
  the Lisp and Curlew don't need it as long as tag traps mean errors.
- **For RFC 0029:** a guard page below the stack is the largest single
  saving here (4.6%); the page map gives it, if the system's layout
  leaves an unmapped page below each stack.
- **For the study:** the field update and the rest above; none of them
  changes the finding on the tagged operations, which rests on how often
  checks find thunks, and they reduce that only at the hot sites.
