# The C compiler

A compiler from a subset of C89 to draft 1a and draft 1b assembly, through
an intermediate representation that knows nothing about C or about either
instruction set.

**Short version.**

- **What it compiles:** all of C89's statements and operators, `char`,
  `short`, `int` and `long` (signed and unsigned), pointers, arrays,
  structs, unions, enums, typedefs, function pointers, variadic functions
  and initialized data, with a real preprocessor and a small C library
  (printf, string functions, malloc). No floating point, `long long` or bit
  fields yet.
- **How:** C → preprocessor → parser and type checker → SSA IR → optimiser
  → instruction selection for 1a or 1b → register allocation (graph
  colouring with coalescing) → assembly → an object file, which the linker
  combines with the start code, the C library and any hand-written
  assembly ([infra/linking.md](../../infra/linking.md)).
- **How good the code is:** on the 15 benchmark programs, the code the
  compiler makes from a program runs in about **1.2× the cycles** of the
  hand-written assembly versions (geometric mean over the programs that
  don't spend most of their time in the C library; 1.0–1.6× each).
  Whole programs take about 1.85× as long, mostly because printf is slower
  than the assembly versions' special-purpose print routines.
- **For the ISA decision:** compiled code gains less from 1b than
  hand-written code does: 1b takes **6% fewer cycles than 1a** for compiled
  C, against 7.5% for the hand-written versions of the same 15 programs
  (D16-overlap; 8.1% over all 20 draft 1 programs, as in
  [RFC 0004](../../reports/0004-rfc-draft-1-isa.md)). The compiler uses 1b's
  auto-increment and memory operands, but loses on its 4-bit constants. See
  [report 0011](../../reports/0011-report-c-compiler.md#1a-against-1b-for-compiled-code).

The numbers are in [report 0011](../../reports/0011-report-c-compiler/performance.md),
generated by `heron c_compiler bench --write`.

## Using it

```sh
heron c_compiler cc --isa v1b prog.c --run            # compile, link and run on the simulator
heron c_compiler cc --isa v1a prog.c --run --stats    # also cycles for all six configurations and a profile
heron c_compiler cc --isa v1b prog.c                  # write the executable prog.out (heron v1_isa run prog.out)
heron c_compiler cc --isa v1b -S prog.c               # just write the assembly, prog.s
heron c_compiler cc --isa v1b -c prog.c               # an object file, prog.o
heron c_compiler cc --isa v1b a.c b.c util.s --run    # several files make one program, assembly too
heron c_compiler cc --isa v1b prog.c --emit-ir        # print the optimised IR
heron c_compiler cc --isa v1b prog.c --run --input 'text\n'   # console input
```

Other options: `-O0` (only promote variables to registers, no other
optimisation), `-I dir`, `-D NAME=value`, `-W` (show warnings), `--no-lib`,
`--no-start` (no start code: the program brings its own vectors), `--map`
(where the linker put everything), `--verify` (check the IR after every
pass), `--input-file FILE` (console input from a file), `--max-cycles N`
(stop the run after N cycles; 500 million by default). `heron c_compiler cc`
is the same command on its own, with `--isa` (default `v1b`).

Each C file is compiled on its own into an object file; the linker adds the
start code and the C library, and keeps only the functions and data that
`main` can reach. [infra/linking.md](../../infra/linking.md) covers object files, the linker
and mixing C with assembly.

Tests:

```sh
python3 -m unittest tests.test_cc tests.test_compiler   # C programs against gcc's output, unit tests
python3 tests/cc/fuzz.py --count 100                    # random programs against gcc
python3 tests/cc/gen_expected.py                        # rewrite tests/cc/expected/ with gcc
heron c_compiler bench                                  # compiled C against the assembly programs
```

## The language

| | |
|---|---|
| Types | `char` (unsigned, see below), `signed char`, `unsigned char`, `short`, `int`, `long` (all 32 bits but `char` 8 and `short` 16), unsigned variants, pointers, arrays, structs, unions, enums, `void`, function pointers, typedefs, `const` and `volatile` |
| Statements | all of C89, including `switch` with fall-through, `goto`, `do`/`while` |
| Expressions | all of C89's operators, casts, `sizeof`, string literals, the comma operator |
| Functions | prototypes and `()` declarations, variadic functions (`<stdarg.h>`), passing and returning structs by value, recursion |
| Data | initializers with brace elision, string initializers for `char` arrays, addresses of globals and functions in static initializers, `static` locals |
| Preprocessor | `#include`, object- and function-like macros, `#` and `##`, `__VA_ARGS__`, `#if` and friends with `defined`, `#error`, `__FILE__`, `__LINE__` |
| C99 extras | `//` comments, declarations after statements and in `for`, designated initializers, `<stdint.h>`, `<stdbool.h>`, `__func__` |
| Not supported | `float`/`double`, `long long`, bit fields, K&R-style function definitions, compound literals, variable-length arrays |

Implementation choices:

- **Plain `char` is unsigned**, because both drafts' byte loads zero-extend
  (only 1a has a sign-extending load). `'\xff'` is 255.
- `int`, `long` and pointers are 32 bits. `>>` of a negative number is
  arithmetic, division rounds toward zero, and dividing by zero traps
  (divide error) like the hardware does. Signed overflow wraps in practice,
  but the optimiser assumes, as C allows, that signed arithmetic doesn't
  overflow: it uses that to prove that values such as loop counters are
  non-negative, and to rewrite compares.
- The headers are in `studies/c_compiler/cc/include`: `stdio.h` (console only: `putchar`,
  `getchar`, `puts`, `printf` with `%d %i %u %x %X %o %c %s %p %%`, flags,
  width and precision; `sprintf`, `snprintf`), `string.h`, `stdlib.h`
  (`malloc`/`free`/`realloc`, `atoi`, `strtol`, `qsort`, `bsearch`, `rand`,
  `exit`), `ctype.h`, `stdarg.h`, `stddef.h`, `limits.h`, `assert.h`, and
  `heron.h` for the I/O page (`HERON_CONSOLE`, `HERON_TIMER`, `HERON_CYCLES`, ...).
  The library itself is C, in `studies/c_compiler/cc/lib`, compiled once per run into a
  library of object files that the linker searches.
- `exit` and `abort` halt the machine; a trap prints `TRAP` and halts.

## Calling convention

The program-wide conventions of [RFC 0004](../../reports/0004-rfc-draft-1-isa.md#13-software-conventions):

- Arguments in `r1`–`r4`, the rest on the stack; the result in `r1`.
- `r1`–`r7` are caller-saved, `r8`–`r14` callee-saved, `r15` is `sp`. `HI`
  and the flags are caller-saved.
- A **variadic** function gets every argument on the stack, so `va_list` is
  just a pointer that walks up the stack, one word per argument.
- A **struct argument** is passed as the address of a copy the caller
  makes. A function **returning a struct** gets the address to store it at
  as a hidden first argument.
- C names get a leading underscore in the assembly (`main` is `_main`), so
  they can't clash with register names, mnemonics or the assembly
  library's labels. An assembly routine that follows these conventions can
  be called from C, under an underscored name or through an assembler name
  on its declaration: `extern void print_u32(unsigned) __asm__("print_u32");`
  (see [infra/linking.md](../../infra/linking.md#c-and-assembly-together)).

The stack frame, from `sp` upwards:

```
sp ->   outgoing stack arguments (reserved once; sp doesn't move in the body)
        local arrays, structs and variables whose address is taken
        spill slots
        callee-saved registers the function uses (one SAVE ra-rb)
        return address
        the caller's stack arguments for this function
```

A function that needs none of this has no prologue at all: a leaf function
is its body and a `RET`.

### The IR

The IR is SSA over 32-bit words, in basic blocks, close to LLVM or QBE in
spirit but much smaller:

```
func dot(%a.0, %b.1, %n.2) {
b0.entry:
  %1 = gt %n.2, 0
  br %1, b7.preheader, b4.endfor
b7.preheader:
  %2 = shl %n.2, 2
  %3 = add %a.0, %2
  jmp b2.for
b2.for:
  %4 = phi [%b.1, b7.preheader], [%11, b2.for]
  %5 = phi [%a.0, b7.preheader], [%12, b2.for]
  %6 = phi [%10, b2.for], [0, b7.preheader]
  %7 = load.32 %5
  %8 = load.32 %4
  %9 = mul.nsw %7, %8
  %10 = add.nsw %6, %9
  %11 = add %4, 4
  %12 = add %5, 4
  %13 = ltu %12, %3
  br %13, b2.for, b4.endfor
b4.endfor:
  %14 = phi [0, b0.entry], [%10, b2.for]
  ret %14
}
```

(That is `for (i = 0; i < n; i++) s += a[i] * b[i];` after optimisation:
the loop has been rotated, `a[i]` and `b[i]` have become pointers, and the
counter `i` is gone.)

- **Values:** constants, symbol addresses (`@name+offset`), parameters,
  stack slots (their value is their address) and instruction results.
- **Instructions:** `add sub mul divs divu rems remu and or xor shl shr sar
  rotr`, compares (`eq ne lt le gt ge` and unsigned `ltu leu gtu geu`,
  giving 0 or 1), `neg not`, `copy`, extensions (`sext8 zext8 sext16 zext16`),
  `load.u8/s8/u16/s16/32`, `store.8/16/32` (with a volatile flag),
  `memcpy`, `call`, `vastart`, `phi`; terminators `jmp br ret switch
  unreachable`.
- `add`, `sub` and `mul` carry an `nsw` flag ("can't overflow as signed
  arithmetic") when they come from C's signed `int` arithmetic, where
  overflow is undefined. The optimiser uses it to prove that values such
  as loop counters are never negative, and to compare `x + k` with `c + k`
  instead of `x` with `c`.
- Memory accesses carry their size and signedness; values in registers are
  always whole words, kept sign- or zero-extended according to their C type.

Nothing in it is specific to C: a frontend for another language would build
it with `ir.ir.Builder`, the way `studies/c_compiler/cc/irgen.py` does, and get the
optimiser and both backends. Nothing in it is specific to an ISA either,
except one hook: the optimiser asks the backend which constants an
instruction can take for free (`free_imm`), to decide which to keep in
registers across a loop (a `copy` of the constant before the loop).

### The optimiser

`ir.passes.optimize` runs, per function:

1. **mem2reg:** every local variable starts as a stack slot; those whose
   address is never taken become SSA values (phis at the iterated
   dominance frontier, renaming over the dominator tree). `char` and
   `short` variables keep their wrap-around through explicit extensions.
2. **Simplification and constant folding**, to a fixed point together with
   the next three: algebraic identities, strength reduction of multiplies,
   divides and remainders by powers of two (signed ones too, with a cheap
   proof that the value is non-negative, which makes `i % 32` an `and`),
   rotates (`x >> n | x << 32 - n`), branch folding, compares rewritten so a
   counter dies at its decrement (`while (n--)`).
3. **Global value numbering** over the dominator tree.
4. **Redundant load elimination** and store-to-load forwarding within a
   block (with a simple distinct-object alias check).
5. **Dead code elimination and control-flow cleanup** (unreachable blocks,
   jump threading through empty blocks, block merging).
6. **Loop-invariant code motion** into a made-up preheader.
7. **Strength reduction of induction variables:** `base + i * k` in a loop
   becomes a pointer stepped by `k`; multiplies of the counter become
   additions; and when the counter is only left to end the loop, the test
   moves to a pointer instead (linear function test replacement).
8. **Constants into registers:** constants that the target can't take as a
   cheap immediate are loaded once before a (call-free) loop.
9. **Sinking:** a step like `p + 1` moves below the last use of `p`, so the
   two share a register and the loop needs no copy on its back edge.

The frontend helps too: loops come out rotated (the test is at the bottom
and runs once more on entry), and blocks are placed in source order.

### The backends

Both backends share `studies/c_compiler/codegen/target.py`, and differ only in instruction
selection and a few peepholes.

**Instruction selection** walks each block of the SSA form. A value with a
single use in the same block (and, for a load, no store or call before that
use) is *folded*: it isn't computed on its own, and the instruction that
uses it is free to absorb it into an operand or addressing mode, or to
compute it on the spot. Address expressions are split into a displacement,
a symbol or stack slot, and scaled registers (`studies/c_compiler/codegen/addr.py`), and
each backend fits as much as it can into one addressing mode.

- **1b** uses memory operands for `MOV ADD SUB CMP AND OR XOR` (when a
  load has one use), every addressing mode (`[r + d16]`, the indexed
  `[r + rx*s + d8]` also with `r0` or `sp` as the base, `[label + r]`,
  stack slots), **auto-increment** when a pointer is stepped by the access
  size next to the access (as in `*p++`, or a strength-reduced loop),
  `LEA` as a three-address add, `INC`/`DEC`, the one-parcel constants,
  `CALL`/`JMP` through memory, and `LEA rt, [pc + table]`, `JMP [rt + r*4]`
  for dense switches.
- **1a** uses base + displacement and `[label + r]` addresses (the
  assembler picks the one-parcel short forms), immediate operands for every
  ALU function, `ADDI`, sign-extending loads, `LEA` as a three-address add,
  and a table jump through a register (`LD r, [table + r]`, with the table
  declared `.far`).

A switch table goes in its function's section, so the PC-relative address
on 1b and the 32-bit displacement on 1a reach it wherever the linker puts
the function.

Two-address instructions are written as `COPY d, a; OP d, b`, choosing which
operand to copy so that the copy is likely to disappear.

**Register allocation** is iterated register coalescing (George and Appel,
as in Appel's *Modern Compiler Implementation*): graph colouring with
conservative coalescing of the copies, calls modelled as clobbering
`r1`–`r7`, so values live across calls go to callee-saved registers.
Spilled values go to stack slots, except constants, which are recomputed at
each use instead. Colours are chosen to coalesce copies that are left and to
use as few callee-saved registers as possible.

**After allocation:** phi copies (sequentialised as parallel copies, on
split critical edges), the frame, a `SAVE`/`RESTORE` of exactly the
callee-saved registers used, and some peepholes: copies that coalesced away,
`MOV rd, rs; ADD rd, x` into `LEA`, compares against 0 or −1 dropped when
the previous instruction already set N and Z, constants folded back into
immediates, jump threading, return blocks duplicated into their
predecessors, branches inverted to fall through, and **tail calls** (a call
followed by a return, when the callee can't need this frame).

### What the code looks like

`dot` from above, and a string copy:

```c
int dot(const int *a, const int *b, int n)
{
    int i, s = 0;
    for (i = 0; i < n; i++)
        s += a[i] * b[i];
    return s;
}

char *copy(char *d, const char *s)
{
    char *r = d;
    while ((*d++ = *s++) != 0)
        ;
    return r;
}
```

```
; draft 1a                          ; draft 1b
_dot:   CMP  r3, #0                 _dot:   CMP  r3, #0
        BGT  .b7                            BGT  .b7
        MOV  r4, #0                         MOV  r3, #0
        MOV  r1, r4                         MOV  r1, r3
        RET                                 RET
.b7:    LSL  r3, #2                 .b7:    LEA  r6, [r1 + r3*4]
        ADD  r3, r1                         MOV  r3, #0
        MOV  r4, #0                 .b2:    MOV  r5, [r1]+
.b2:    LD   r6, [r1]                       MOV  r4, [r2]+
        LD   r5, [r2]                       MULS r5, r4
        MULS r5, r6                         ADD  r3, r5
        ADD  r4, r5                         CMP  r1, r6
        ADDI r2, 4                          BLO  .b2
        ADDI r1, 4                          MOV  r1, r3
        CMP  r1, r3                         RET
        BLO  .b2
        MOV  r1, r4
        RET

_copy:  LDB  r4, [r2]               _copy:  MOV  r4, byte [r2]+
        INC  r2, r2                         ST   r4, byte [r1]
        STB  r4, [r1]                       INC  r3, r1
        INC  r3, r1                         CMP  r4, #0
        CMP  r4, #0                         BNE  .b3
        BNE  .b3                            RET
        RET                         .b3:    MOV  r4, byte [r2]+
.b3:    LDB  r4, [r2]                       ST   r4, byte [r3]+
        INC  r2, r2                         CMP  r4, #0
        STB  r4, [r3]                       BNE  .b3
        INC  r3, r3                         RET
        CMP  r4, #0
        BNE  .b3
        RET
```

The first copy of the loop body in `copy` is the rotated loop's entry test
(C's `while` evaluates the condition, with its side effects, before the
first iteration).

## Testing

- `studies/c_compiler/tests/test_cc.py` compiles every program in `studies/c_compiler/tests/cc/` for both drafts
  and checks the output against what gcc's build of it prints (written to
  `studies/c_compiler/tests/cc/expected/` by `gen_expected.py`, with `-funsigned-char`). The
  programs cover arithmetic of every width, control flow, pointers,
  structs, calls, initialized data and some algorithms.
- `studies/c_compiler/tests/test_compiler.py` has unit tests: the preprocessor, error
  messages, that given optimisations happen, that given instructions are
  used, and some small programs. It also runs every test program's IR,
  before and after optimisation, on the IR interpreter
  (`studies/c_compiler/ir/interp.py`), which checks the optimiser without the backends.
- `studies/c_compiler/tests/cc/fuzz.py` generates random programs (all integer types,
  arrays, structs, loops that walk arrays, switches, calls) and compares
  the compiler's output for both drafts with gcc's. The programs have no
  undefined behaviour: the generator keeps a bound on each `int` value,
  leaves arithmetic signed where it can't overflow (so the optimiser's
  `nsw` assumptions above get tested), and does it in `unsigned` where it
  might. gcc builds the reference with `-fsanitize=undefined`, which
  catches a program the generator got wrong. The fuzzer found five bugs
  during development: a tail call that freed a stack frame still in use,
  a loop test moved onto a value that wasn't an address, a rewrite that
  referred to an instruction already deleted, the register allocator
  spilling rematerialised constants forever, and a peephole that looked at
  the wrong instructions when reusing flags. `studies/c_compiler/tests/cc/regress.c` keeps the last one.
- `heron c_compiler bench` checks the 15 benchmark programs.

## Limitations and next steps

- **No floating point, `long long` or bit fields.** `long long` would be
  the most useful next (the ISA has `ADC`/`SBC` and `MULU`'s high half);
  software floating point after that.
- **Separate compilation costs a little** (0.9% at most on the
  benchmarks): with no linker relaxation, a call to another function always
  takes two parcels, and arrays over 1 KB get 32-bit addresses
  ([infra/linking.md](../../infra/linking.md#what-it-costs)).
- **The compiler misses:**
  - shrink-wrapping (saving callee-saved registers only on the paths that
    need them: half of fib's calls return at once but still pay for a
    `SAVE`/`RESTORE`);
  - keeping a loaded value across loop iterations;
  - inlining;
  - splitting live ranges around calls;
  - a better block layout than source order.
- **Interrupt handlers can't be written in C yet:** they'd need an
  attribute that saves every register and returns with `RTI`.
- **A new ISA draft** needs a new `studies/c_compiler/codegen/vN.py` with instruction
  selection, and a start-up file in `studies/c_compiler/cc/lib`; the IR, the optimiser,
  the register allocator and the rest of the backend carry over. For 1a
  with auto-increment, the 1b backend's `find_postinc` would move over
  almost unchanged.
